# План исправлений Office Wallet

Документ описывает **как закрыть** каждую строку реестра из [README](../README.md) и **что изменится** для пользователей, ролей и эксплуатации после фикса. Пути — относительно `app/`, если не указано иное.

## Как читать

| Поле | Смысл |
| --- | --- |
| Статус | `открыто` / `частично` / `закрыто` по текущему дереву |
| Фикс | Конкретное изменение в коде или конфигурации |
| Что изменится | Поведение после внедрения |
| Проверка | Как убедиться, что дефект закрыт |

Уже закрытые (OW-08, 09, 14, 15, 21, 27, 31–33, 35) оставлены кратко: что уже сделано и что ещё желательно добить.

## Деньги и заказы

### OW-01 — Переполнение при расчёте покупки

**Статус:** открыто · **Место:** `internal/app/handlers_shop.go` → `checkoutQuote`

**Фикс.** Перед `chargeKop := dbSum - dbSum*promo/100 + tipKop` проверять диапазоны: `tipKop` и результат через безопасное сложение (отклонять, если `tipKop > MaxInt64 - discounted` или `promoPct` вне 0…100). Отрицательный `chargeKop` — ошибка, не обнуление «в пользу» покупателя без явной политики.

**Что изменится.** Котировка с гигантскими чаевыми или переполненным `tip_kop` получит 400/flash «некорректная сумма» вместо нулевой или абсурдной цены. Легитимные заказы с нормальными чаевыми без изменений.

**Проверка.** POST `/checkout/quote` с `tip_kop=9223372036854775807` → отказ; обычная корзина → прежняя сумма.

---

### OW-02 — Оформление по несогласованной котировке

**Статус:** открыто · **Место:** `checkoutConfirm`

**Фикс.** В `checkout_quotes` сохранять снимок корзины (`lines_json` / hash состава) при создании котировки. В confirm сравнивать текущую корзину со снимком; при расхождении — отказ и новая котировка. Не полагаться только на `anomaly_log`.

**Что изменится.** Нельзя оплатить старую цену после подмены позиций в корзине. Пользователю нужно заново пройти quote при изменении корзины.

**Проверка.** Quote → изменить qty/товар → confirm → отказ.

---

### OW-03 — Неатомарное оформление

**Статус:** открыто · **Место:** `checkoutConfirm`

**Фикс.** Одна транзакция: `SELECT … FOR UPDATE` котировки (`used=false`), проверка баланса, списание, `used=true`, INSERT заказа, очистка корзины, INSERT operation. Любая ошибка — полный rollback.

**Что изменится.** Не будет «списали, но заказ не создали» и повторного проведения одной котировки параллельными запросами. При сбое БД пользователь увидит ошибку и сможет повторить с новой котировкой.

**Проверка.** Два параллельных confirm одной `quote_id` → ровно один заказ.

---

### OW-04 — IDOR заказа / отмены

**Статус:** частично (владелец уже проверяется) · **Место:** `orderView`, `orderCancel`

**Фикс.** Считать IDOR закрытым для сотрудника. Добить: единый helper `loadOrderForUser(id, u)` для view/cancel/return/received/preview; кассир — только чтение + fulfill. Атомарность отмены — в OW-06.

**Что изменится.** Поведение для честных пользователей то же. Чужой `/orders/N` по-прежнему 404.

**Проверка.** Сотрудник A не открывает и не отменяет заказ B.

---

### OW-05 — Некорректный размер возврата

**Статус:** открыто · **Место:** `orderReturn`

**Фикс.** Считать возврат по оплаченным позициям: `refund = min(requested, remaining_refundable)`. Запретить `qty <= 0` и `refund > total` (или остаток). Хранить уже возвращенную сумму / статус `returned` без повторного полного зачисления.

**Что изменится.** `qty=100` больше не начисляет `100×total`. Форма возврата может показывать максимум к возврату.

**Проверка.** Заказ 450 ₽, `qty=100` → отказ или max 450 ₽; повторный возврат → отказ.

---

### OW-06 — Неатомарные возвраты и отмены

**Статус:** открыто · **Место:** `orderCancel`, `orderReturn`

**Фикс.** `UPDATE orders SET status=… WHERE id=$1 AND status IN (…) RETURNING …` + зачисление баланса в одной транзакции. Условие по статусу делает вторую гонку no-op.

**Что изменится.** Двойной клик / параллельная отмена не удвоит возврат.

**Проверка.** Два параллельных POST cancel → один refund в `operations` и одно зачисление.

---

### OW-07 — Изменение статуса при GET

**Статус:** открыто · **Место:** `orderReceived`, ссылка в `templates/order.html`

**Фикс.** Только POST (или POST+CSRF). В шаблоне — форма с кнопкой вместо `<a href="…/received">`.

**Что изменится.** Prefetch/сканер ссылок и CSRF через `<img>`/`GET` больше не переводят заказ в `received`. Пользователь нажимает кнопку «Получил».

**Проверка.** GET `/orders/N/received` → 405; POST меняет статус.

**Что изменится.** Неактивный `product_id` не попадёт в корзину; пользователь увидит ошибку при сбое БД.

## Переводы, чаевые, платежи

### OW-12 — XSS

**Статус:** открыто · **Место:** `history` (`QRaw`), `tipsReceived` (`TipHTML`)

**Фикс.** Убрать `template.HTML` для пользовательского ввода; выводить обычные строки (автоэкранирование). Удалить `sanitizeSearchDisplay` как «защиту». `Preview` в чеке — только после `HTMLEscapeString` (уже так).

**Что изменится.** Поиск и комментарии чаевых показываются как текст, скрипты не исполняются. Вёрстка в комментариях чаевых перестанет быть HTML.

**Проверка.** Чаевые с `<ScRiPt>alert(1)</ScRiPt>` → текст на экране, нет выполнения.

### OW-13 — Избыточный доступ к операциям

**Статус:** открыто · **Место:** `apiOpsFeed`, `operation`

**Фикс.** Feed: только операции, где пользователь участник (или роль admin/accountant). Не выставлять `op_grant_*` на чужие id. В `operation` оставить grant только для явной безопасной схемы (или убрать cookie-grant).

**Что изменится.** Сотрудник не перечисляет чужие операции и не открывает их по токену из feed.

### OW-17 — Replay платежа

**Статус:** открыто · **Место:** `payReplay`, `pay.js`

**Фикс.** Либо удалить `/pay/replay`, либо: одноразовый nonce в БД, TTL подписи, плательщик = текущий user в HMAC, запрет `to_login` ≠ signed recipient. Подпись: `op_id:amount:recipient:payer:exp:nonce`.

**Что изменится.** Нельзя крутить одну подпись многократно и подменять получателя. UI «повторить» создаёт новый draft перевода.

**Проверка.** Два POST с одной `sig` → второй отказ.

### OW-18 — SSRF через редирект

**Статус:** кандидат · **Место:** `doNotify`

**Фикс.** `http.Client{CheckRedirect: func(...) error { return http.ErrUseLastResponse }}` или проверка каждого `Location` на тот же host/scheme/path-prefix. Не следовать на внешние URL.

**Что изменится.** Callback на mock без цепочки редиректов наружу. Если mock отдаёт 302 — приложение не пойдёт за ним (или пойдёт только на allowlist).

**Статус:** открыто (импакт низкий/не подтверждён как денежный) · **Место:** `transferConfirm`, `transfer_confirm.html`

**Что изменится.** В журнале kind всегда соответствует черновику (`transfer`), клиент не подставит `tip_boss`.

## Аутентификация и сессии

### OW-23 — Brute-force входа

**Статус:** открыто · **Место:** `login`

**Фикс.** Лимит попыток по login + IP (таблица / redis / in-memory с backoff). После N неудач — временная блокировка или CAPTCHA. Единый timing ответа.

**Что изменится.** После серии ошибок — задержка или «попробуйте позже». Легитимный вход после 1–2 ошибок без изменений.

---

### OW-24 — Ошибка bcrypt при регистрации

**Статус:** открыто (импакт теоретический) · **Место:** `register`

**Фикс.** `hash, err := hashPassword(pass); if err != nil { … отказ }`. Политика пароля (длина).

**Что изменится.** При невозможности захэшировать аккаунт не создаётся.

---

### OW-25 — Fallback кода сброса

**Статус:** открыто (импакт теоретический) · **Место:** `randomSMSCode`

**Фикс.** При ошибке `rand.Int` — не выдавать код, вернуть 500/«сервис недоступен».

**Что изменится.** Нет предсказуемого кода от времени; редкий сбой ГСЧ станет отказом сервиса, а не слабым кодом.

---

### OW-26 — Сброс пароля: лимит попыток

**Статус:** частично (TTL 15 мин + атомарное погашение есть) · **Место:** `passwordReset`

**Фикс.** Счётчик попыток на `password_resets` / IP; после N неверных — `used=true` или lockout. Опционально увеличить энтропию кода.

**Что изменится.** Перебор 6 цифр за 15 минут станет непрактичен. Верный код с первой–второй попытки работает как сейчас.

### OW-27 — Почта — закрыто

**Место:** `mailBox` · Только admin видит outbox.

### OW-28 — Обход блокировки

**Статус:** частично (роль уже из БД) · **Место:** `currentUser` / `requireUser`

**Фикс.** Если `u.Blocked` — считать сессию недействительной (как logout), кроме, при желании, страницы «заблокирован».

**Что изменится.** Заблокированный сотрудник сразу теряет доступ ко всем handler’ам, даже со старой cookie.

**Проверка.** Accountant блокирует user → следующий запрос user → редирект на login.

---

### OW-29 — Сессии без срока и отзыва

**Статус:** открыто · **Место:** `signSession`, `setSession`

**Фикс.** В подпись добавить `exp` (например 12h) и/или `session_version` в БД; при смене пароля / logout — bump version. Опционально таблица `sessions`.

**Что изменится.** Украденная cookie протухнет; смена пароля инвалидирует старые сессии. Пользователей периодически попросят войти снова.

---

### OW-30 — Флаги cookie

**Статус:** частично · **Место:** `setSession`, `apiOpsFeed`

**Фикс.** `Secure: true` при HTTPS (флаг конфига). `op_grant_*`: HttpOnly + SameSite=Strict или отказаться от cookie-grant (OW-13).

**Что изменится.** На HTTP-стенде Secure может ломать cookie — включать по `PUBLIC_BASE`/env. XSS не прочитает grant-cookie.

### OW-34 — PostgreSQL: секреты и TLS

**Статус:** открыто · **Место:** `docker-compose.yml`, `cmd/wallet/main.go`, Helm

**Фикс.** Пароль только из secret/env (уже частично для keys). `sslmode=verify-full` с CA в Compose/Helm для non-dev. Сменить дефолт `wallet:wallet` в документации стенда на генерацию при первом подъёме.

**Что изменится.** Трафик app↔db шифруется; дефолтный пароль не торчит в репозитории для prod-подобных values. Локальный lab может оставить disable за явным `DEV_INSECURE=1`.

### OW-36 — Секреты в CI

**Статус:** частично (печать убрана) · **Место:** `ci/app-credentials.sh`

**Фикс.** Процесс: ротация `POSTGRES_PASSWORD` / `SESSION_KEY` / `PAYMENT_KEY` в кластере, где когда-то печатали секреты. В скрипте — запрет `echo` значений навсегда (code review / grep в CI).

**Что изменится.** Старые утёкшие значения перестанут работать после ротации; пользователям сбросятся сессии при смене `SESSION_KEY`.

### OW-40 — CSRF на POST

**Статус:** открыто · **Место:** все state-changing формы

**Фикс.** CSRF-токен в сессии + hidden field; middleware на POST/PUT/DELETE. Дополнительно проверка `Origin`/`Referer` same-site. Вместе с OW-07.

**Что изменится.** Поддельный сайт не проведёт перевод/отмену без токена. Все формы получат скрытое поле; сломаются самописные скрипты без токена (poc нужно обновить).

---

### OW-41 — Security headers

**Статус:** открыто · **Место:** `render`, опционально middleware в `ListenAndServe`

**Фикс.** На HTML-ответы:
- `Content-Security-Policy: default-src 'self'; …` (fonts — self или SRI)
- `X-Frame-Options: DENY` / `frame-ancestors 'none'`
- `X-Content-Type-Options: nosniff`

**Что изменится.** Страницу нельзя встроить в iframe (clickjacking сложнее); XSS ограничен CSP; MIME-sniffing отключён. Внешние Google Fonts — либо self-host, либо `style-src` + SRI (ADD-01).

### OW-42 — Контейнер от root

**Статус:** открыто · **Место:** `app/Dockerfile`

**Что изменится.** Процесс не uid 0; последствия RCE/shell (OW-38) уже. Нужно, чтобы volume exports был writable для этого uid.

### OW-43 — Утечка ошибок БД

**Фикс.** Клиенту — нейтральное «внутренняя ошибка»; детали только в server log.

**Что изменится.** В браузере не будет текста `pq: …`; в логах приложения — полная ошибка для отладки.

| Переводы / replay | Повтор подписи, подмена получателя | Один платёж = один draft/nonce |
| Чаевые / история | XSS через регистр | Текст экранируется |
| Вход / сброс | Без лимитов; блок не действует на сессию | Rate limit; blocked сразу; сессии с TTL |
| Каталог / себестоимость | Канал в API, cost любому | Cost только уполномоченным |
| Админ-журнал / notify | Всем; shell по ticket | Только admin; без exec |
| Браузер | Нет CSP/CSRF | Токены на формах, заголовки, без clickjacking |
| Контейнер | root | non-root user |

PoC в `poc/` после фиксов нужно обновить или пометить ожидаемым отказом — это критерий приёмки.
