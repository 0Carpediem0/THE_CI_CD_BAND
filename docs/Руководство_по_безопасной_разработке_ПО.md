# Руководство по разработке безопасного программного обеспечения

Регламенты процессов Office Wallet по ГОСТ Р 56939-2024

## 1. Общие положения

1.1. Настоящее Руководство устанавливает порядок организации и выполнения процессов разработки безопасного программного обеспечения (далее — РБПО) при создании, доработке, сопровождении и выводе из эксплуатации программного обеспечения Office Wallet (корпоративный кошелёк сотрудников) и иных программных компонентов, разрабатываемых организацией самостоятельно в интересах указанного продукта.

1.2. Руководство разработано на основе ГОСТ Р 56939-2024 «Защита информации. Разработка безопасного программного обеспечения. Общие требования» (утверждён приказом Росстандарта от 24.10.2024 № 1504-ст).

1.3. Цель РБПО (п. 4.1 ГОСТ Р 56939-2024):

- выявление недостатков, в том числе уязвимостей, в разрабатываемом ПО;
- снижение количества недостатков, в том числе уязвимостей ПО;
- снижение ущерба от невыявленных уязвимостей ПО;
- оперативное устранение выявляемых уязвимостей в ПО.

1.4. Процессы РБПО реализуются комплексом организационных и технических мероприятий при участии руководства и при выделении необходимых ресурсов (пп. 4.5, 4.6 ГОСТ Р 56939-2024).

1.5. В тексте настоящего Руководства (п. 4.7 ГОСТ Р 56939-2024):

- «должен», «следует» — обязательные условия соответствия;
- «рекомендуется» — рекомендация;
- «может» — допустимое действие.

1.6. Требований к оформлению регламентов ГОСТ Р 56939-2024 не предъявляет. Регламенты процессов сведены в настоящий документ (п. 4.12 ГОСТ Р 56939-2024).

1.7. Сведения о ходе РБПО, результаты исследований и тестирования подлежат защите: разграничение доступа, защищённое хранение, антивирусный контроль носителей и рабочих мест (п. 4.17 ГОСТ Р 56939-2024).

## 2. Нормативные ссылки

В настоящем Руководстве использованы ссылки на:

- ГОСТ Р 56939-2024;
- ГОСТ Р ИСО/МЭК 12207 (жизненный цикл ПО — для соотнесения этапов при необходимости);

## 3. Область применения процессов РБПО

3.1. Процессы РБПО применяются к следующему составу ПО (п. 5.1.2.5, п. 5.1.3.5 ГОСТ Р 56939-2024):

- серверное приложение Office Wallet (каталог app/, язык Go);
- вспомогательный сервис уведомлений notify-mock (каталог mock/);
- скрипты сборки и развёртывания (scripts/, charts/office-wallet/, docker-compose.yml);
- конвейер непрерывной интеграции (.gitlab-ci.yml, ci/).

3.2. Обоснование выбора состава: перечисленные компоненты содержат исходный код, конфигурацию сборки и поставки, непосредственно влияют на безопасность обработки денежных операций и учётных данных. Готовые сторонние образы (PostgreSQL, Mailpit) в область собственной разработки не входят; в отношении них выполняются процессы управления конфигурацией и композиционного анализа в части используемых версий и известных уязвимостей.

3.3. Настоящее Руководство обязательно для работников, участвующих в разработке, проверке, сборке, выпуске и сопровождении ПО, указанного в п. 3.1.

## 4. Организационная структура и роли

4.1. Организацию и внедрение процессов РБПО обеспечивает руководитель проекта (владелец продукта).

4.2. Роли при реализации процессов:

| Роль | Функции и полномочия |
| --- | --- |
| Руководитель проекта | утверждает настоящее Руководство и планы РБПО; выделяет ресурсы; принимает решения о выпуске версии при наличии неустранённых замечаний |
| Ответственный за РБПО | координирует процессы 5.1–5.25; ведёт учёт артефактов; инициирует анализ текущего состояния; контролирует исполнение планов |
| Разработчик | пишет и изменяет код; соблюдает правила кодирования; устраняет недостатки по задачам; не обходит проверки конвейера |
| Эксперт по безопасности (AppSec) | проводит экспертизу кода, моделирование угроз, разбор результатов SAST/DAST/SCA; ведёт реестр уязвимостей; готовит рекомендации по нейтрализации угроз |
| Инженер сборки / DevOps | обеспечивает безопасность сборочной среды, секретов, конвейера CI/CD, поставки артефактов |
| Тестировщик | выполняет функциональное и нефункциональное тестирование, в том числе проверки исправлений уязвимостей |
| Контролёр процессов | проверяет выполнение регламентов и полноту артефактов; по возможности не совмещает роль с ролью разработчика того же изменения |

4.3. Контроль исполнения процессов РБПО осуществляет контролёр процессов и (или) руководитель проекта. Результаты контроля фиксируются в системе управления задачами либо в акте (записи) проверки.

## 5. Среда разработки и инструменты

5.1. Среда разработки должна обеспечивать (п. 4.13 ГОСТ Р 56939-2024):

- контроль версий исходного кода;
- непрерывную интеграцию;
- управление задачами, в том числе учёт ошибок и уязвимостей.

5.2. Применяемые инструменты (состав может уточняться приказом / записью ответственного за РБПО):

| Назначение | Инструмент |
| --- | --- |
| Контроль версий | Git, удалённый репозиторий (GitHub / GitLab / Origin) |
| Управление задачами | Issues / Pull Request в репозитории проекта |
| Непрерывная интеграция | GitLab CI (.gitlab-ci.yml) либо аналог |
| Сборка и контейнеризация | Docker, scripts/build-images.sh, Helm-чарт charts/office-wallet |
| Статический анализ (SAST) | gosec, golangci-lint (по решению ответственного за РБПО) |
| Композиционный анализ (SCA) | govulncheck, анализ go.mod / go.sum |
| Динамический анализ / проверки на стенде | ручные сценарии, poc/ (только на изолированном стенде), при наличии — ZAP или аналог |
| Учёт уязвимостей | README (реестр), docs/FIXES.md, SECURITY.md, задачи в трекере |

5.3. Процессы РБПО следует интегрировать со средой разработки так, чтобы проверки выполнялись регулярно, а устранение выявленных ошибок было прослеживаемым (п. 4.13 ГОСТ Р 56939-2024).

## 6. Порядок взаимодействия работников

6.1. Изменение кода вносится через ветку и запрос на слияние (pull/merge request). Прямая запись в основную ветку без проверки не допускается, за исключением аварийных исправлений по письменному решению руководителя проекта с последующим оформлением запроса.

6.2. До слияния должны быть выполнены применимые проверки: экспертиза и (или) автоматический анализ, сборка, тесты. Замечания по безопасности блокируют слияние до устранения либо до принятия риска руководителем проекта с фиксацией в задаче.

6.3. Обнаружение уязвимости в ходе разработки или эксплуатации оформляется задачей с указанием критичности. Срок устранения определяет ответственный за РБПО с учётом критичности; критические недостатки не допускается выпускать в эксплуатационную поставку без компенсирующих мер и решения руководителя проекта.

6.4. Разработка и тестирование выполняются на выделенных стендах. Разработку и отладку непосредственно в промышленной (эксплуатационной) среде проводить запрещается.

6.5. Перенос готовой версии в эксплуатационную среду выполняет инженер сборки / DevOps по утверждённой процедуре выпуска (раздел 7, процесс 5.20).

## 7. Регламенты процессов разработки безопасного ПО

Ниже для каждого процесса раздела 5 ГОСТ Р 56939-2024 приведены: наименование, цели, порядок реализации в организации, роли, артефакты. Нумерация процессов совпадает с нумерацией стандарта.

### 7.1. Процесс 5.1. Планирование процессов разработки безопасного программного обеспечения

**Цели:** обеспечение ресурсами; подготовка и планирование внедрения и улучшения процессов; определение области применения.

**Порядок реализации:**

- не реже одного раза в год (а также при существенном изменении состава ПО) ответственный за РБПО проводит анализ текущего статуса реализации процессов 5.1–5.25;
- по результатам анализа обновляются область применения (раздел 3), план развития и план реализации процессов;
- планы утверждает руководитель проекта.

**Роли:** ответственный за РБПО — подготовка; руководитель проекта — утверждение.

**Артефакты:** описание области применения; результаты анализа статуса; план развития процессов; план реализации процессов (допускается ведение в системе управления задачами).

### 7.2. Процесс 5.2. Обучение сотрудников

**Цели:** актуализация знаний о практиках РБПО; снижение типовых ошибок и уязвимостей.

**Порядок реализации:**

- ответственный за РБПО не реже одного раза в год анализирует доступные материалы по безопасной разработке (в том числе применительно к Go, веб-приложениям, работе с секретами и зависимостями);
- составляется план обучения с перечнем работников, сроками и темами;
- проводится обучение (внутреннее или внешнее); ведётся учёт прохождения;
- критерии пересмотра программ: смена технологического стека, появление критических классов уязвимостей в продукте, изменение нормативной базы.

**Роли:** ответственный за РБПО; все работники, указанные в п. 3.3.

**Артефакты:** результаты анализа материалов; план обучения; журнал (учёт) прохождения обучения.

### 7.3. Процесс 5.3. Формирование и предъявление требований безопасности к программному обеспечению

**Цели:** наличие и актуальность требований безопасности к ПО; прослеживаемость их реализации.

**Порядок реализации:**

- для новых функций и существенных изменений AppSec совместно с разработчиком формулирует требования безопасности (аутентификация, авторизация, валидация ввода, атомарность денежных операций, защита секретов, журналирование и т.п.);
- требования включаются в описание задачи / техническое задание на изменение;
- при приёмке изменения проверяется выполнение требований безопасности.

**Роли:** AppSec; разработчик; тестировщик; руководитель проекта (утверждение приоритетов).

**Артефакты:** набор (перечень) требований безопасности; записи в задачах; результаты приёмки.

### 7.4. Процесс 5.4. Управление конфигурацией программного обеспечения

**Цели:** идентификация элементов конфигурации; контроль изменений; воспроизводимость сборок.

**Порядок реализации:**

- элементами конфигурации являются: исходный код, файлы сборки, конфигурация CI, Helm-values, схема БД, документация по безопасности;
- изменения фиксируются в системе контроля версий с осмысленным сообщением о фиксации;
- выпуску версии присваивается идентификатор (тег / номер версии образа).

**Роли:** разработчик; инженер сборки / DevOps.

**Артефакты:** репозиторий; перечень элементов конфигурации (допускается в README / каталоге charts); теги выпусков.

### 7.5. Процесс 5.5. Управление недостатками и запросами на изменение программного обеспечения

**Цели:** учёт недостатков и запросов; приоритизация; контроль устранения.

**Порядок реализации:**

- каждый недостаток (в том числе уязвимость) и запрос на изменение регистрируются в трекере;
- для уязвимостей указываются идентификатор (например, OW-NN), критичность, место в коде, статус устранения;
- закрытие задачи допускается только при наличии подтверждения исправления (код, тест, повторная проверка).

**Роли:** все роли; приоритизацию уязвимостей ведёт AppSec.

**Артефакты:** задачи трекера; реестр уязвимостей; docs/FIXES.md.

### 7.6. Процесс 5.6. Разработка, уточнение и анализ архитектуры программного обеспечения

**Цели:** архитектура, допускающая реализацию требований безопасности; выявление архитектурных недостатков.

**Порядок реализации:**

- при проектировании существенных изменений описываются границы доверия, роли, хранилища данных, внешние интерфейсы (HTTP API, БД, SMTP, notify-mock);
- AppSec анализирует архитектуру на предмет нарушения разграничения доступа, небезопасных потоков данных и единых точек отказа безопасности;
- замечания устраняются до начала массовой реализации либо принимаются с фиксацией риска.

**Роли:** разработчик; AppSec; руководитель проекта.

**Артефакты:** описание архитектуры (документ или раздел в docs/); результаты анализа архитектуры.

### 7.7. Процесс 5.7. Моделирование угроз и разработка описания поверхности атаки

**Цели:** снижение недостатков, связанных с архитектурой и логикой; актуальная модель угроз и поверхность атаки.

**Порядок реализации:**

- первичная модель угроз и описание поверхности атаки составляются для Office Wallet (входные точки: веб-формы, API, cookie-сессии, экспорт, notify callback, административные маршруты, касса, бухгалтерия);
- для актуальных угроз определяются меры нейтрализации;
- модель и поверхность атаки уточняются при существенных изменениях интерфейсов или не реже одного раза в год;
- формируется перечень целей для углублённых исследований (в том числе динамического анализа).

**Роли:** AppSec; разработчик (уточнение интерфейсов).

**Артефакты:** модель угроз ПО; описание поверхности атаки; перечень целей исследований.

### 7.8. Процесс 5.8. Формирование и поддержание в актуальном состоянии правил кодирования

**Цели:** единые правила безопасного кодирования; снижение типовых ошибок.

**Порядок реализации:**

- действуют правила: параметризованные запросы к БД; запрет конкатенации пользовательского ввода в SQL и shell; экранирование вывода в шаблонах; проверка прав на сервере; атомарность денежных операций в транзакциях; секреты только из окружения / secret store; запрет демонстрационных ключей в поставке;
- правила доводятся до разработчиков при обучении и в настоящем Руководстве;
- пересмотр — при появлении новых классов дефектов в реестре уязвимостей.

**Роли:** AppSec (актуализация); разработчик (соблюдение).

**Артефакты:** раздел настоящего Руководства; замечания в code review.

### 7.9. Процесс 5.9. Экспертиза исходного кода

**Цели:** выявление недостатков путём экспертного разбора кода до включения в основную ветку.

**Порядок реализации:**

- каждое изменение проходит экспертизу как минимум одним работником, не являющимся единственным автором изменения (по возможности);
- особое внимание: обработка денег, сессии, права доступа, разбор ввода, криптография, работа с файлами и внешними URL;
- результаты фиксируются в запросе на слияние.

**Роли:** разработчик (автор); эксперт / второй разработчик / AppSec.

**Артефакты:** записи code review в запросах на слияние.

### 7.10. Процесс 5.10. Статический анализ исходного кода

**Цели:** автоматическое выявление потенциальных недостатков в исходном коде.

**Порядок реализации:**

- статический анализ выполняется в конвейере CI и (или) локально перед запросом на слияние;
- срабатывания размечаются: истинное / ложное / принято с риском;
- истинные срабатывания высокой и критической важности подлежат устранению до выпуска.

**Роли:** инженер сборки / DevOps (встраивание); разработчик; AppSec (разметка).

**Артефакты:** отчёты анализатора; разметка срабатываний в задаче или отчёте.

### 7.11. Процесс 5.11. Динамический анализ кода программы

**Цели:** выявление недостатков при выполнении ПО, в том числе с подачей некорректных и граничных данных.

**Порядок реализации:**

- на изолированном стенде выполняются сценарии проверки безопасности (в том числе по реестру уязвимостей и poc/ — только против стенда);
- рекомендуется применение сканера веб-уязвимостей и при необходимости фаззинг выбранных интерфейсов из перечня целей (п. 7.7);
- результаты передаются в процесс 5.5.

**Роли:** AppSec; тестировщик.

**Артефакты:** отчёты динамических проверок; записи в трекере.

### 7.12. Процесс 5.12. Использование безопасной системы сборки программного обеспечения

**Цели:** воспроизводимая и контролируемая сборка; снижение риска подмены артефактов.

**Порядок реализации:**

- сборка выполняется зафиксированными скриптами и Dockerfile из репозитория;
- артефакты сборки (образы) маркируются тегом версии;
- ручная «сборка с рабочей станции» для эксплуатационной поставки не рекомендуется; предпочтительна сборка в CI.

**Роли:** инженер сборки / DevOps.

**Артефакты:** журналы CI; теги образов; скрипты сборки в репозитории.

### 7.13. Процесс 5.13. Обеспечение безопасности сборочной среды программного обеспечения

**Цели:** защита инфраструктуры сборки от несанкционированного доступа и подмены.

**Порядок реализации:**

- доступ к CI и registry разграничивается учётными записями;
- секреты CI не выводятся в журналы (см. также процесс 5.15);
- обновления базовых образов сборки планируются ответственным за РБПО.

**Роли:** инженер сборки / DevOps; ответственный за РБПО.

**Артефакты:** описание (схема) сборочной среды; политика доступа; журналы доступа CI (при наличии).

### 7.14. Процесс 5.14. Управление доступом и контроль целостности кода при разработке программного обеспечения

**Цели:** предотвращение несанкционированного изменения кода; контроль целостности.

**Порядок реализации:**

- права на запись в основную ветку ограничены;
- аутентификация в репозитории — по персональным учётным данным / ключам;
- целостность фиксируется хешами коммитов; при поставке — контрольными суммами / подписями образов (при применении).

**Роли:** руководитель проекта (модель доступа); инженер сборки / DevOps.

**Артефакты:** модель (описание) доступа к репозиториям; журнал изменений прав (при ведении).

### 7.15. Процесс 5.15. Обеспечение безопасности используемых секретов

**Цели:** исключение хранения и утечки секретов в коде и журналах.

**Порядок реализации:**

- SESSION_KEY, PAYMENT_KEY, пароли БД и аналогичные секреты не хранятся в исходном коде и не коммитятся в репозиторий;
- для локального стенда секреты задаются через переменные окружения (.env, не включаемый в поставку);
- сервер должен отказывать в запуске при пустых и демонстрационных ключах;
- при компрометации выполняется ротация секретов.

**Роли:** инженер сборки / DevOps; разработчик.

**Артефакты:** политика работы с секретами (настоящий раздел); отсутствие секретов в истории коммитов (контроль); записи о ротации.

### 7.16. Процесс 5.16. Использование инструментов композиционного анализа

**Цели:** учёт заимствованных компонентов; выявление известных уязвимостей в зависимостях.

**Порядок реализации:**

- зависимости фиксируются в go.mod / go.sum;
- периодически (не реже чем перед выпуском) выполняется проверка известных уязвимостей (govulncheck или аналог);
- уязвимые компоненты обновляются либо риск принимается руководителем проекта с фиксацией.

**Роли:** разработчик; AppSec; инженер сборки / DevOps.

**Артефакты:** перечень зависимостей; отчёты SCA.

### 7.17. Процесс 5.17. Проверка кода на предмет внедрения вредоносного программного обеспечения через цепочки поставок

**Цели:** снижение риска внедрения вредоносного кода через заимствования и поставщиков.

**Порядок реализации:**

- заимствуемый код и образы берутся из доверенных источников;
- перед включением стороннего фрагмента выполняется экспертиза и антивирусная проверка носителя / архива при получении вне пакетного менеджера;
- неожиданные изменения зависимостей в запросе на слияние подлежат отдельному разбору.

**Роли:** разработчик; AppSec; инженер сборки / DevOps.

**Артефакты:** результаты проверок; записи в запросах на слияние.

### 7.18. Процесс 5.18. Функциональное тестирование

**Цели:** подтверждение соответствия ПО функциональным требованиям, в том числе после исправления уязвимостей.

**Порядок реализации:**

- для изменений составляются и выполняются тест-кейсы;
- исправление уязвимости сопровождается проверкой, что дефект не воспроизводится, и регрессионной проверкой смежных функций (платежи, вход, заказы);
- результаты фиксируются.

**Роли:** тестировщик; разработчик.

**Артефакты:** планы и отчёты функционального тестирования; записи в задачах.

### 7.19. Процесс 5.19. Нефункциональное тестирование

**Цели:** проверка свойств безопасности, надёжности и устойчивости.

**Порядок реализации:**

- выполняются проверки на отказ в обслуживании в допустимых пределах стенда, на утечки информации в ответах об ошибках, на соблюдение таймаутов и ограничений пула соединений;
- негативные тесты по границам сумм, прав доступа, повторному использованию токенов и кодов сброса включаются в регрессию по мере закрытия пунктов реестра уязвимостей.

**Роли:** тестировщик; AppSec.

**Артефакты:** отчёты нефункционального тестирования.

### 7.20. Процесс 5.20. Обеспечение безопасности при выпуске готовой к эксплуатации версии программного обеспечения

**Цели:** выпуск версии, для которой выполнены предусмотренные проверки; учёт остаточных рисков.

**Порядок реализации:**

- перед выпуском проверяется выполнение процессов 5.9–5.19 в объёме, применимом к изменению;
- неустранённые недостатки перечисляются в решении о выпуске с оценкой риска;
- фиксируются сведения о версии и месте хранения дистрибутива (образа).

**Роли:** руководитель проекта; ответственный за РБПО; инженер сборки / DevOps.

**Артефакты:** решение (запись) о выпуске; перечень неустранённых замечаний; сведения о версии и хранении артефакта.

### 7.21. Процесс 5.21. Безопасная поставка программного обеспечения пользователям

**Цели:** доставка подлинного и целостности артефакта пользователю (эксплуатационной среде).

**Порядок реализации:**

- поставка выполняется из доверенного registry / согласованного канала;
- передаются инструкции по установке и перечень обязательных параметров (в том числе требование задать SESSION_KEY и PAYMENT_KEY);
- рекомендуется проверка контрольных сумм / подписей при их применении.

**Роли:** инженер сборки / DevOps.

**Артефакты:** канал поставки; сопроводительные сведения о версии; README / NOTES чарта.

### 7.22. Процесс 5.22. Обеспечение поддержки программного обеспечения при эксплуатации пользователями

**Цели:** сопровождение ПО; исправление ошибок и уязвимостей в сроки, согласованные с критичностью.

**Порядок реализации:**

- обращения и сообщения об ошибках принимаются через трекер;
- для уязвимостей действует порядок процесса 5.23;
- пользователям (эксплуатирующему подразделению) сообщаются способы получения обновлений и ограничения поддержки.

**Роли:** ответственный за РБПО; разработчик; руководитель проекта.

**Артефакты:** регламент поддержки (настоящий раздел); журнал обращений.

### 7.23. Процесс 5.23. Реагирование на информацию об уязвимостях

**Цели:** своевременная обработка сведений об уязвимостях; снижение ущерба.

**Порядок реализации:**

- источник сведений: внутренние проверки, пользователи, внешние сообщения;
- каждая уязвимость регистрируется, оценивается по критичности, назначается исполнитель и срок;
- по итогам выпускается исправление либо документируется компенсирующая мера;
- при необходимости информируются заинтересованные стороны.

**Роли:** AppSec; ответственный за РБПО; руководитель проекта.

**Артефакты:** журнал сообщений об уязвимостях; записи об оценке критичности и сроках; выпуски исправлений.

### 7.24. Процесс 5.24. Поиск уязвимостей в программном обеспечении при эксплуатации

**Цели:** регулярное выявление уязвимостей в эксплуатируемом ПО.

**Порядок реализации:**

- периодически проводятся повторные статический и композиционный анализ актуальной ветки, а также выборочные динамические проверки на стенде, соответствующем эксплуатационной конфигурации;
- рекомендуется привлечение внешних экспертов или участие в программах поиска уязвимостей при наличии ресурсов (как усиление);
- находки передаются в процесс 5.23.

**Роли:** AppSec; ответственный за РБПО.

**Артефакты:** регулярные отчёты проверок.

### 7.25. Процесс 5.25. Обеспечение безопасности при выводе программного обеспечения из эксплуатации

**Цели:** безопасное прекращение использования ПО; защита остаточных данных.

**Порядок реализации:**

- при выводе из эксплуатации отключаются точки входа, отзываются ключи и учётные записи интеграций;
- носители и тома с данными обрабатываются по правилам организации (очистка / уничтожение / архивирование);
- пользователи уведомляются о прекращении поддержки.

**Роли:** руководитель проекта; инженер сборки / DevOps.

**Артефакты:** акт (запись) о выводе из эксплуатации; подтверждение отзыва секретов и отключения сервисов.

## 8. Контроль выполнения настоящего Руководства

8.1. Контролёр процессов не реже одного раза в квартал выборочно проверяет:

- наличие актуальных артефактов по процессам, выполнявшимся в периоде;
- соблюдение порядка слияния изменений и работы с секретами;
- состояние реестра уязвимостей и сроков устранения.

8.2. Выявленные нарушения оформляются задачей с указанием срока устранения.

8.3. Изменения в настоящее Руководство вносятся ответственным за РБПО и утверждаются руководителем проекта. С новой редакцией знакомят работников, указанных в п. 3.3.

## 9. Заключительные положения

9.1. Настоящее Руководство вступает в силу с даты утверждения.

9.2. Неприменимость отдельных требований ГОСТ Р 56939-2024 к конкретному компоненту ПО допускается только при письменном обосновании особенностями этого ПО, согласованном ответственным за РБПО и руководителем проекта (с фиксацией в анализе текущего статуса, процесс 5.1).

9.3. При противоречии между краткими формулировками настоящего документа и текстом ГОСТ Р 56939-2024 приоритет имеет стандарт в части обязательных требований («должен», «следует»).
