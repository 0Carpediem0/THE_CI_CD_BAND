Анализ безопасности «Office Wallet»

Корпоративный кошелёк (Go + PostgreSQL + Mailpit + notify-mock)
Команда: The CI/CD band · Дата: 26 ноября 2026
Объект: локальный стенд docker compose (http://localhost:18081), образ work-app:latest; боевой контур — *.devsecops-contest.ru
Режим: белый ящик (исходники + образ), подтверждение по сети приложения.

Окружение и метод

Стенд собран из репозитория: docker compose up -d --build. Приложение (образ work-app, база debian:bookworm-slim) слушает :8080, опубликовано на 18081; PostgreSQL 16, Mailpit и notify-mock — отдельные сервисы. Учётки сида: ivanov/workplace1 (сотрудник), а также kassa (кассир), buch (бухгалтер), adminw (администратор).

PoC написаны под cookie-сессии приложения (новый клиент poc/kept/wallet_client.py; прошлый KeptExpliots/_http.py рассчитан на Token-API другого стенда и не подходит). Прогон: docker run --rm --network work_default -v <poc>:/poc -w /poc python:3-alpine python run_all.py --base http://app:8080. Сканеры: Trivy 0.76.2 (образ + репозиторий), Nuclei 3.11.1 (стенд), заголовки — curl.

Файлы: app/internal/app/. В curl-примерах используется подделанная кука на дефолтном SESSION_KEY=office-wallet-session-key; на боевом ключе значение иное, но способ тот же.

VULN-01. Ключи подписи захардкожены и утекают в клиентскую статику Critical · CVSS 9.8

CWE / OWASP. A02:2021 / A05:2021 · CWE-798, CWE-321, CWE-547
CVSS. Critical · CVSS 9.8 — оценка самой уязвимости, не цепочки.
Steps to Reproduce.
SESSION_KEY и PAYMENT_KEY имеют дефолтные значения, прошитые в коде и compose, и вдобавок по частям собираются в статике, отдаваемой каждому браузеру. Любой анонимный клиент восстанавливает оба ключа.
Код. 
// app/cmd/wallet/main.go
SessionKey: env("SESSION_KEY", "office-wallet-session-key"),
PaymentKey: env("PAYMENT_KEY", "office-wallet-pay-key"),

// app/static/pay.js        -> "office-wallet-pay-key"
// app/static/wallet.js + legacy-sync.js -> "office-wallet" + "-session-key"
Предусловия. Нет (анонимно); либо доступ к исходникам/образу.
PoC. poc/kept/01_key_leak_static_js.py
Воспроизведение. 
curl -s http://localhost:18081/static/pay.js
curl -s http://localhost:18081/static/wallet.js
curl -s http://localhost:18081/static/legacy-sync.js
# PAYMENT_KEY = office-wallet-pay-key ; SESSION_KEY = office-wallet-session-key
Результат. Оба ключа восстановлены и приняты сервером (подделанная admin-кука = 200). Все HMAC-механизмы (сессия, платёж, op-grant, supply-channel) скомпрометированы.
Remediation. Падать на старте при пустом/дефолтном/коротком ключе; удалить ключи из статики; op-grant и supply-channel не отдавать наружу. См. fixes/PATCHES.md (VULN-01).

VULN-07. Инфляция возврата заказа (refund = total × qty) High · CVSS 8.1

CHAIN-01. Захват аккаунта и эскалация до администратора CVSS цепочки 8.1

Состав. VULN-36 + VULN-08 + VULN-02 + VULN-37 + VULN-38. Запасной код OW-25 отдельной карточки не имеет: срабатывает только при отказе crypto/rand.
VULN-36→ VULN-08→ VULN-02 / VULN-37→ VULN-38→ админ и удержание сессии
Сценарий. Неограниченный подбор пароля открывает учётку. Если пароль не подобран, тот же вход ведёт на сброс: код из 6 цифр без счётчика. Дальше роль поднимается до admin, потому что она читается из cookie, а флаг blocked не проверяется. Сессия без отзыва оставляет доступ после выхода. С admin открываются журнал операций и канал закупочных цен (VULN-20, VULN-12).
PoC цепочки. poc/stage_access.py — брут входа, сброс, blocked и жизнь сессии после logout. Отдельные шаги: poc/kept/15_password_reset_ato.py, poc/kept/02_session_forge_admin.py.
Итоговый импакт. На этом стенде — захват учётки жертвы (почта сброса кода не содержит, шлюз SMS только для admin из таблицы users). Подделка роли не даёт admin: после проверки подписи роль берётся из БД, дефолтный ключ из статики сервер отвергает. Удержание сессии после выхода подтверждено.
CVSS цепочки. 8.1 — CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H. Полный сценарий до admin при живой подделке роли был бы 9.8 (AC:L, тот же CIA). На стенде звено VULN-02 не поднимает роль, поэтому балл — у захвата учётки.
Что рвёт цепочку. Быстрее всего — Remediation VULN-08 (код из crypto/rand, срок, лимит попыток): без сброса захват нечем завершить. Подделка admin уже оборвана Remediation VULN-02.

CHAIN-02. XSS → чужие операции → перевод от жертвы CVSS цепочки 7.3

Состав. VULN-13 + VULN-14 + VULN-22 + VULN-15 + VULN-11 + VULN-23 + VULN-09.
VULN-13 / VULN-14→ VULN-22→ VULN-11→ VULN-09→ чужие операции и перевод
Сценарий. Жертва открывает чаевые или поиск в истории, скрипт исполняется на том же сайте: CSP нет. Запрос уходит с её сессией. Лента отдаёт grant на чужие операции; у op_grant_* нет HttpOnly, скрипт его читает. Подпись повторного платежа уже лежит в истории жертвы, повтор списывает её счёт. Кука ow_session из JS не читается.
PoC цепочки. Отдельного скрипта нет. Сквозной прогон — PoC VULN-13 или VULN-14, затем запрос к /pay/replay и /api/ops/feed с той же сессией (poc/kept/12_payment_replay_forge.py, poc/kept/10_idor_ops_feed.py, poc/stage_xss.py).
Итоговый импакт. Чтение чужих финансовых операций и перевод денег от имени жертвы.
CVSS цепочки. 7.3 — CVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:U/C:H/I:H/A:N.
Что рвёт цепочку. Remediation VULN-13 (не выводить пользовательский текст как template.HTML; то же закрывает VULN-14). Без исполнения скрипта grant и повтор платежа от жертвы не запускаются.

CHAIN-03. Списание через CSRF без XSS CVSS цепочки 4.3

Состав. VULN-23 + VULN-33 + VULN-39 + VULN-09.
страница атакующего→ VULN-23→ VULN-33 / VULN-39→ VULN-09→ списание
Сценарий. Залогиненная жертва открывает страницу атакующего. GET меняет статус заказа. POST без CSRF-токена отправляет чаевые и подтверждение перевода с подменённым op_type. Повтор платежа множит списание. XSS не нужен.
PoC цепочки. poc/stage_money.py и poc/stage_registry_extra.py проверяют GET-смену статуса, гонку чаевых и подмену op_type отдельными запросами с сессией. Сквозной cross-site POST в этих скриптах не собран.
Итоговый импакт. На этом стенде — смена статуса своего заказа, если жертва загрузит чужую страницу. Списания нет: SameSite=Lax не отправляет куку на cross-site POST, VULN-39 меняет только вид проводки.

CHAIN-04. Нарушение целостности денег CVSS цепочки 8.1

Состав. VULN-29 + VULN-16 + VULN-07 + VULN-30 + VULN-31 + VULN-33 + VULN-35 + VULN-34 + VULN-17 + VULN-32. OW-31 и OW-15 отдельных карточек не имеют: перевод рублей в копейки отвергает ParseInt, черновик перевода снимается в транзакции.
VULN-29или VULN-16или VULN-07или VULN-30 / VULN-31
Сценарий. В записи CHAINS переполнение суммы, чужая котировка, возврат total×qty, гонки и кассовые операции складываются в неограниченный рост баланса. На стенде это параллельные дыры, не одна стрелка. Заказ за 0 имеет total_kop = 0, возврат его не умножает. Кассовый минус и повторный возврат на выдаче требуют роль cashier в таблице users.
PoC цепочки. poc/stage_money.py (заказ за 0, возврат с qty, отрицательное пополнение) и poc/stage_registry_extra.py (гонки котировки, возврата, чаевых). Итог каждого шага — в карточке звена; общего скрипта «сложить все дыры в один баланс» нет, прогон показывает, что они не умножают друг друга.
Итоговый импакт. Самый тяжёлый подтверждённый исход — печать денег возвратом своего заказа. Недоплата по старой котировке, заказ за 0 и повторное зачисление — отдельные потери. Хищение через кассу — только с ролью cashier.
CVSS цепочки. 8.1 — балл VULN-07. Выше него цепочка не поднимается: звенья не усиливают друг друга.
Что рвёт цепочку. Одного фикса на все развилки нет. Наибольший выход закрывает Remediation VULN-07 (возврат только уплаченной суммы, один раз). Заказ за 0 закрывает Remediation VULN-29.

CHAIN-05. RCE → контейнер → база и латераль CVSS цепочки 7.4

Состав. VULN-03 + VULN-20 + VULN-19 + VULN-18 + VULN-26 + VULN-24.
VULN-03 / VULN-20→ VULN-19→ VULN-18→ VULN-26 / SSRF

Итоговый импакт. На этом стенде RCE нет. Доступ к БД есть отдельно: пароль wallet/wallet из compose, если Postgres доступен в сети стенда. Дальше приложение не нужно. Root в образе и секреты CI остаются самостоятельными находками.
CVSS цепочки. 7.4 — балл VULN-18, это достигнутый доступ к БД, не следствие RCE. Живой RCE под root был бы 9.9, как у VULN-03.
Что рвёт цепочку. Remediation VULN-20 и VULN-03 (убрать exec и сборку шаблона из пользовательской строки) — код не запускается. Доступ к БД это не закрывает: его рвёт Remediation VULN-18.
